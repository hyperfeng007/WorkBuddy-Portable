# 1.0.1：任务请求的 407 修复

## 用户现象与已复现缺陷

用户在 1.0.0 中发消息/执行任务，错误报告包含：

```text
statusCode: 407
407 Proxy authentication required
(proxy: undefined -> https://www.workbuddy.cn)
```

随后提供的网络摘要中，其他 daemon/desktop 请求可以返回 200。两者不矛盾：**同一应用有不同的网络实现**，普通 fetch 成功不能证明任务引擎的 Axios/CLI 路径也成功。

本次重新取得与 1.0.0 完全相同、SHA-256 匹配的官方原始包，检查错误文本生成逻辑和实际任务网络代码，确认遗漏：

1. 官方 `main/index.js` 的 `createElectronHostNetwork.resolveProxy` 返回 Chromium 的 `session.defaultSession.resolveProxy` 结果。
2. 返回形式例如 `PROXY 127.0.0.1:端口`，不包含便携桥接认证。
3. `cli/dist/codebuddy-headless.js` 和 `cli/dist/codebuddy-lite-wb.mjs` 各自包含独立 `ProxyResolver`。它们的 `resolveForUrl` 优先采用 L0 PAC hook，再考虑环境变量。
4. 因而即使 HTTP_PROXY/HTTPS_PROXY 中已有正确认证，这条任务请求仍可能拿到无认证代理 URL。
5. 1.0.0 只适配了主进程/daemon 的 `main/proxy-agents.js`，没有适配这两份 CLI 的独立解析器。这是社区封装的遗漏，不应通过关闭桥接认证或要求用户反复换代理来掩盖。

错误提示里的 `proxy: undefined` 来自 CLI 的错误分析逻辑，不等于“完全没有用代理”。9485 连接拒绝、另一些 401/422 摘要也不足以单独确定这个 407 的原因；本版不为这些未查明情况盲改服务或账号配置。

## 修复内容

新增 `source/patch_cli.go` 和内嵌 `assets/portable-cli-proxy.cjs`：

- 仅针对已审核官方构建的两份原文件，先校验整文件 SHA-256、大小和唯一锚点。
- 仅在便携启动器环境中，异步 `resolveForUrl` 和同步 `resolve` 都优先返回当前启动器拥有的认证桥接 URL，避免重新经过会丢失认证的 PAC 分支。
- helper 验证桥接是指定形态的本机 HTTP endpoint；口令来自当前启动器运行环境，不持久化到产品代理设置，不把口令塞进会被上游打印的 PAC 规则。
- loopback 保持直接连接。真实上游选择仍由同一 Go 桥接按启动器的 auto/manual/direct 配置决定。
- 使用 `source: env`，避免触发上游仅对 system 来源使用的关闭 TLS/直连重试逻辑；没有关闭认证或证书校验。
- 同步更新 ASAR 中两个 unpacked 条目的大小和 SHA-256/block integrity，再重算 EXE 中的 ASAR header 摘要。仍保持 Electron 完整性 fuse 开启，签名边界与 1.0.0 一致。
- 每次复用增加两个 CLI 文件与 ASAR 中记录的整文件哈希核对，能检测同大小的内容损坏。

原始文件 SHA-256：

```text

cli/dist/codebuddy-lite-wb.mjs

```

其余通用代理、桥接认证机制和官方构建不换代；不修改 DSH 1.0.4。

## 不是仅检查字符串：实际传输回归

`TestCLIProxyAuthenticationRegression` 使用真实官方两份 CLI 中的 resolver 代码，在隔离 VM 中执行；经真实 `https-proxy-agent`、本包实际 Go 桥接和测试上游 CONNECT 代理访问受信任的 TLS fixture。

每份 CLI 都执行了下面的对照：

- **旧代码**：提供正确认证环境变量，同时提供 Chromium 形态 PAC hook；实际构造的代理 URL 没有认证，真实 Go 桥接返回 **407**，正文为 `Proxy authentication required\n`。
- **Go 实际打补丁的代码**：相同条件下提供正确桥接认证，经同一上游隧道得到目标 **200** 和有效中文 JSON。
- **错误口令**：仍得到 **407**，证明不是通过放开匿名代理让测试“通过”。
- 同步 resolver 和 loopback 行为均有断言。

这是可复现、与用户症状吻合的代码缺陷和修复证据；不是对用户账号的线上任务成功率或所有 Windows 原生组件作保证。

## 本地缓存与升级

1.0.1 的常规修复准备优先检查 `Runtime/packages/<固定SHA256>.exe`。缓存完整且哈希正确时，不请求更新 feed，也不重新下载官方包，直接在新 stage 本地解包适配；即使准备时无网络也不依赖 feed。**AI 服务本身仍需要网络**。

显式 `--update` / Update-WorkBuddy.cmd 仍检查官方元数据，不自动接受未经审核的新官方构建。缺失/损坏的缓存不能保证免下载，已有记录时会提示确认下载。准备仍要求 6 GiB 空闲空间。

不要只是把 `current.json` 的 wrapper 改成 1.0.1：必须实际更新两份 CLI、ASAR 完整性及 EXE 摘要。启动器会完成这些操作，保留 Data 和旧运行时，成功后切换指针。

## 升级步骤

- 将本包 EXE 覆盖到**原便携目录**，保留原 Data / Runtime / tools / portable.json。
- 本发行包特意不附默认 portable.json，避免解压覆盖现有代理；没有配置文件时程序默认 auto。
- 正常启动并允许本地重新适配，等主界面加载后试一条简单消息。
- 官方 App Version 仍为 5.6.2；便携启动器文件属性为 1.0.1.0，当前运行时记录 wrapper 为 1.0.1。
